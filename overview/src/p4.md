P4 builds what runs above the boot chain and the pipeline that builds it: the CC's operating-system image (Yocto or Buildroot, P1 `docs/01-system-description.md` §1.4) with a read-only, integrity-checked root filesystem, a single service holding the signing key, confined parsers, a USB allowlist, a hardware watchdog and authenticated maintenance logins; the CC's MAVLink command filter and its logging (DD-04); and the MSS build pipeline with hash-pinned dependencies, SBOMs, vulnerability scans and build provenance (P1 `README.md`; `docs/07-requirements.md` §7.2). P4 owns {{p1.repo_reqs:P4}} requirements.

**Inherited from P2.**

- **The root filesystem (SR-006).** P2's chain ends at the kernel and initramfs; the root filesystem is verified by the kernel with dm-verity, which is P4's (P2 `docs/02-cc-boot-chain.md` §2.2; `docs/01-scope-and-trace.md` §1.5).
- **Runtime integrity.** P2 seals the keys to PCRs 0, 1, 8 and 9 only; PCRs from 10 up change at runtime (IMA, for example) and runtime integrity is left to P4 (P2 `docs/03-measured-boot-sealing.md` §3.1).
- **The A/B layout,** shared with P3, that lets a CC boot its previous chain when a new one cannot unseal (P2 `docs/03-measured-boot-sealing.md` §3.5).
- **The DEBIX image.** P2 boots a busybox initramfs; the hardened image that P4 builds is what the unsealed keys are handed to. P2's hardened U-Boot configuration and its DEBIX fragment (P2 `docs/02-cc-boot-chain.md` §2.4) are inputs to that image's boot loader. *Assumption: P4 keeps U-Boot `v2026.07`, so that P2's PCR prediction carries over; P2's documents do not state this.*
