# P1: the system, its threats and its requirements {#p1}

P1 is the security architecture of a notional, unclassified small UAS built from open-source parts: a PX4 flight controller, a Linux companion computer, a ground control station and a MAVLink command link (P1 `README.md`). It sets down the system, the threats to it, the requirements that answer those threats, and a verification event for every requirement. Every later repository produces evidence for some of those requirements.

P1 keeps its facts in five CSV files under `data/`, which are the single source of truth. Python tools check them and generate the tables in P1's documents (P1 `data/README.md`). This chapter's tables are generated the same way, from P1's data at commit `{{p1.data_commit}}`.

## The system {#p1-system}

The vehicle flies a pre-planned survey pattern within radio line of sight, stores electro-optical imagery on board, streams video to the operator and returns; imagery is offloaded over a wired link after landing (P1 `docs/02-conops.md` §2). Its parts (P1 `docs/01-system-description.md` §1.2):

| ID | Component | Basis | Role in this document |
|---|---|---|---|
| CMP-FC | Flight controller (FC) | PX4 on NuttX, Pixhawk-standard flight management unit | Flies the vehicle. Verifies MAVLink signatures. P2 makes it boot only signed firmware |
| CMP-CC | Companion computer (CC) | ARM64 Linux single-board computer | Terminates the encrypted link from the ground, filters commands, runs autonomy and payload. P2 makes it boot only a signed chain and keep its keys in a TPM |
| CMP-GCS | Ground control station (GCS) | QGroundControl on a Linux laptop | Where the operator plans and commands |
| CMP-MSS | Maintenance and support station (MSS) | Linux workstation, wired connections only | Builds, signs and loads software; provisions keys |
| CMP-RAD-A, CMP-RAD-G | Data-link radios | Generic IP radios | Untrusted transport: no credit is taken for their own encryption (assumption A-05) |

The architecture's first design decision, DD-01, connects the radio to the CC and the CC to the FC, so every command-and-control (C2) path runs ground station → CC → FC (P1 `docs/04-architecture.md` §4.4). ## Protecting command and control {#p1-c2}

Three layers protect commands from the ground (P1 `docs/04-architecture.md` §4.3):

1. **A WireGuard tunnel from GCS to CC** (DD-02) gives confidentiality and peer authentication across the radio link. The CC accepts nothing else on its radio interface (requirement SR-001).
2. **An allowlist filter on the CC** (DD-04) limits which MAVLink messages and commands reach the FC. It is defense in depth, not an authentication point.
3. **MAVLink message signing, GCS to FC.** Each MAVLink 2 frame carries a 48-bit signature computed with SHA-256 over a 32-byte secret key and the frame (P1 `docs/01-system-description.md` §1.3). This end-to-end signing is design intent: it has not yet been shown to work between the pinned QGroundControl and PX4 versions (open item OI-01, closed by verification event VE-02 in P3).

<!-- gen: mermaid-from docs/04-architecture.md 3 -->

*The command path (P1 `docs/04-architecture.md` §4.3). Steps 2 and 8, signing and verification, are design intent until VE-02 passes.*

**The weak point is the signing key.** PX4 uses one shared signing key for every node: the FC, the CC, the GCS and the MSS all hold the same 32-byte secret (P1 `docs/04-architecture.md` §4.2). Two consequences follow, and they are the reason P2 exists:

- **Any key holder can forge any command.** Code running on the CC, or a copy of the CC's key, gives full control of the vehicle: parameter writes, mission upload, arming, flight termination (P1 `docs/04-architecture.md` §4.2, item 1).
- **The CC is the most exposed holder.** It terminates the tunnel, parses traffic from the radio link, runs general-purpose Linux and is powered throughout flight (§4.2, item 2). Protecting it is the job of P2 (what it boots, where its keys live) and P4 (the hardened image).

## Threats {#p1-threats}

P1 analyzes threats with **STRIDE per element**. Each element of the data-flow diagram (process, external entity, data store, data flow) is examined for the six STRIDE categories that apply to its type: **S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service and **E**levation of privilege (P1 `docs/05-threat-model.md` §5.1). Each threat gets a mission-impact rating from MI-1 (loss of vehicle control, or a safety hazard) to MI-4 (negligible). The rating is the consequence if the threat is realized, scored before mitigation, with no likelihood term; the scale is project-defined (assumption A-13; P1 `data/README.md`).

The adversary has three tiers (assumption A-08): (1) RF-proximate, with a software-defined radio, able to jam, eavesdrop and inject; (2) physical access to a lost or captured vehicle or unattended ground equipment; (3) able to insert code through an upstream source or a build host. Tier 2 matters most for P2: a captured vehicle gives an adversary time with its storage, its ports and its circuit board.

In numbers: **{{p1.threats}} threats** on {{p1.stride_elements}} STRIDE elements; by impact {{p1.threat_impacts}}; {{p1.threats_mitigated}} mitigated by requirements and {{p1.threats_accepted}} accepted with a written rationale. Most MI-1 threats end the same way: an adversary holds the shared signing key, or runs code on a node that holds it (P1 `docs/05-threat-model.md`, introduction). The threat P1 ranks first is THR-010, "{{p1.threat_title:THR-010}}" (P1 `docs/05-threat-model.md` §5.3).

## Why P2's requirements exist {#p1-why-p2}

P1 assigns {{p1.repo_reqs:P2}} requirements to P2, {{p1.repo_req_ids:P2}}, verified by {{p1.repo_ves:P2}}. Their parent threats are the reason for each one.

<!-- gen: p1-threats-of P2 -->

*The P1 threats that P2's requirements answer: {{p1.repo_threats:P2}} threats, {{p1.repo_threats_mi1:P2}} of them rated MI-1.*

**SR-005, verified boot of the CC.** THR-008 is a compromise that survives reboot by modifying the CC's boot chain; THR-032 rewrites the CC's storage offline, which a tier-2 adversary with a captured or unattended vehicle can do by removing the SD card. Either way the CC would run attacker code with the signing key and the WireGuard key in reach, which is THR-010. Verified boot means the CC refuses, before running it, any boot-chain component not signed with the project's boot key. P1's assumption A-04 says where the trust starts: the CC's system-on-chip (SoC) has secure boot, whose boot ROM checks the first boot-loader stage against a key hash fused into the chip (P1 `docs/03-assumptions.md`). The concepts behind this are explained in [](#concepts).

**SR-010, keys sealed to the TPM.** THR-034 extracts the CC's copy of the signing key and its WireGuard private key from a captured vehicle; THR-007 uses the stolen WireGuard key to pose as the vehicle; THR-035 replaces the CC's stored trust anchors. Sealing means the keys are stored encrypted by a TPM and released only when the TPM's record of the boot (its measurements) matches an approved state. Removed storage holds only ciphertext that no other TPM can open, and a modified boot chain cannot get the keys. A-04 is explicit that the TPM measures and seals but does not verify: it cannot stand in for secure boot. THR-034 keeps a residual risk after sealing: with time and tools, an adversary can attack the bus between the SoC and the TPM, or replay approved measurements if the TPM can be reset on its own (P1 `docs/05-threat-model.md` §5.5). Physical attacks are P5's scope.

**SR-018, signed FC firmware.** THR-058 loads unsigned firmware through the PX4 USB boot loader, which accepts any image unless secure boot is enabled; THR-030 modifies firmware with physical access; THR-041 tampers with release artifacts between build and load. PX4 Bootloader Secure Boot checks an Ed25519 signature before starting the firmware. Its root of trust is the boot loader in the FC's flash, which sets no write-protection, so SR-018 holds only while SR-024 (P5) keeps the debug port closed (SR-018's rationale in P1 `data/requirements.csv`). It does not stop an *older* signed release from booting: P2 found that gap, and P1 recorded it as THR-066, "{{p1.threat_title:THR-066}}", mitigated by SR-045 in P3 (P2 `docs/01-scope-and-trace.md` §1.4, change 2).

## How P1 checks itself {#p1-checks}

Every push to P1 runs four CI jobs (P1 `.github/workflows/validate.yml`):

- **traceability:** unit tests, then `tools/validate_trace.py`, which fails if a threat is neither mitigated nor accepted, a requirement has no parent threat or no verification event with the same method and repo, an identifier is orphaned, a framework ID is not in its pinned catalog, or an event is marked passed or failed without evidence pinned to a commit (P1 `README.md`, "Verification evidence"). Then `tools/render_views.py --check` and `tools/gen_sysml.py --check`, which fail if a generated document table or the generated SysML v2 model has drifted from the CSVs.
- **sysml:** validates the SysML v2 model with the OMG Pilot Implementation.
- **brief:** builds the eleven-slide brief PDF with a pinned toolchain.
- **overview:** checks the P2 snapshot against P2 and builds this document (`overview/README.md`).

[](#recreate) runs the Python checks on a clean machine, with their expected output.
